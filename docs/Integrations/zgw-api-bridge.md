# ZGW API bridge

The ZGW API bridge connects Pipelinq to the modern Dutch *zaakgericht-werken*
REST stack published by VNG Realisatie: Zaken (ZRC), Documenten (DRC), Besluiten
(BRC), Catalogi (ZTC), Autorisaties (AC) and Notificaties (NRC). It is the
forward-looking counterpart to the legacy `stuf-zkn-bg-adapter`.

## Configuration objects

The bridge stores its configuration as OpenRegister objects in the `pipelinq`
register (added through the `register.d/50-zgw.json` fragment, ADR-037):

| Schema | Purpose |
|--------|---------|
| `zgwEndpoint` | One profile per gemeente: the ZRC/DRC/BRC/ZTC/AC/NRC component URLs, `actief` (write path) and `readOnly` flags. |
| `zgwClient` | VNG-API-Common JWT credentials. Stores only a **vault reference** to the secret, never the secret itself. |
| `nrcAbonnement` | NRC subscription state: registered abonnement URL, callback URL, callback bearer **vault reference**, kanalen + filters. |
| `zgwResourceMapping` | Bidirectional link between a Pipelinq entity (request/contact/document) and a ZGW resource URL, with the cached ETag. |

## App configuration keys

These are tunable through the admin settings (`IAppConfig`, app `pipelinq`):

| Key | Default | Description |
|-----|---------|-------------|
| `zgw.nrc_callback_url` | *(empty)* | The public Pipelinq callback URL the NRC posts notifications to, e.g. `https://pipelinq.zoetermeer.nl/index.php/apps/pipelinq/api/zgw/notificaties/inbox`. |
| `zgw.ztc_cache_ttl` | `3600` | ZTC (catalogi) cache TTL in seconds. |
| `zgw.ac_refresh_interval` | `900` | AC (autorisaties) scope-cache refresh interval in seconds. |
| `zgw.drc_inline_threshold` | `4194304` | DRC inline-upload threshold in bytes (4 MiB). Files above this use the multipart `bestandsdelen` protocol. |

## Secrets and the vault

ZGW credentials are **never** stored in the OpenRegister schema. Each
credential-bearing field holds a `vault://…` reference; the plaintext is held
encrypted-at-rest in Nextcloud app config via `ICrypto` (the same primitive
OpenRegister uses for source credentials) and resolved per request by
`ZgwSecretResolver`.

Reference conventions used by the seed data and the NRC subscription flow:

| Reference | Holds |
|-----------|-------|
| `vault://zgw/<gemeenteCode>/client-secret` | The VNG-API-Common client secret (JWT HS256 signing key). |
| `vault://zgw/<gemeenteCode>/client-cert` | Optional PEM client certificate for mutual TLS. |
| `vault://zgw/<gemeenteCode>/client-key` | Optional mTLS private key. |
| `vault://zgw/<endpointId>/nrc-callback-bearer` | The per-abonnement bearer token used to authenticate inbound NRC callbacks (generated automatically on subscription). |

A gemeente IT team must provision the `client-secret` (and any mTLS material)
**before** setting a `zgwEndpoint` to `actief: true`. The NRC callback bearer is
generated by the bridge when the abonnement is registered.

## Security model

- **Outbound** calls authenticate with a freshly minted HS256 JWT per request
  (VNG-API-Common profile: `iss`/`client_id`/`user_id`/`user_representation`/`iat`/`exp`).
  A clock-skew rejection surfaces as a `ClockSkewException` with both timestamps
  and is never auto-retried.
- **Inbound** NRC notifications hit `POST /api/zgw/notificaties/inbox`. Although a
  public page (the NRC is not a Nextcloud user), every request **must** carry a
  Bearer token that matches the per-abonnement callback secret, compared in
  constant time. Unmatched tokens get a `401` and no body is processed.
- Write operations are guarded client-side by the AC scope cache: a missing
  `zaken.aanmaken` / `besluiten.aanmaken` / `documenten.aanmaken` scope raises
  `InsufficientScopeException` before any HTTP call.

## Coexistence with StUF

During a StUF→ZGW migration both backends may be configured **read-only**, but at
most one may be the active **write** path per gemeente. `ZgwCoexistenceValidator`
raises a `DoubleWritePathException` (before any external call) when both a StUF
endpoint and a ZGW endpoint are write-active for the same `gemeenteCode`. The
StUF side is a soft dependency: when `stuf-zkn-bg-adapter` is not installed there
is no StUF write path and no conflict.

## Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| `ClockSkewException` on every call | The Pipelinq host clock drifts more than ±60s from the ZGW host. Fix NTP synchronisation. |
| `InsufficientScopeException` | The AC has not granted the required scope on the zaaktype/besluittype. Ask the gemeente beheerder to grant it; the cache refreshes within `zgw.ac_refresh_interval`. |
| NRC callbacks return `401` | The stored callback bearer no longer matches, or the abonnement is inactive. Re-register the abonnement. |
| `ZaaktypeNotInCatalogusException` | The zaaktype omschrijving is not published in the ZTC. Publish it or correct the omschrijving. |
| `DoubleWritePathException` | Both StUF and ZGW are write-active for the gemeente. Disable one write path under **Beheer → Integraties**. |
